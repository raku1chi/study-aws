# クラウドネイティブ設計

> **この章のゴール**
> - クラウドネイティブの原則を、疎結合・マネージドサービス・自動化・可観測性といった具体的な設計判断に落とし込める
> - EventBridge を中心としたイベント駆動アーキテクチャで、コレオグラフィとオーケストレーションを使い分けられる
> - Step Functions（Standard / Express、Distributed Map、エラー処理、Saga、タスクトークン）と Lambda durable functions を使い分け、冪等な処理を設計できる
> - マイクロサービス間の通信（同期 / 非同期、Cloud Map、ECS Service Connect、VPC Lattice）と入口（API Gateway / AppSync / ALB）を選べる。App Mesh からの移行先を説明できる
> - ECS / EKS / Fargate / EKS Auto Mode のコンテナ戦略と、スキャン・署名・最小権限・シークレット注入・ランタイム監視を含むコンテナセキュリティを設計できる
> - Database per service、CQRS、イベントソーシング、トランザクションアウトボックス、キャッシュの各パターンを使い分けられる
>
> **対応試験**: SAP-C03（D1 クラウドネイティブアーキテクチャの設計と実装 ※ドメイン名は仮訳）。SAP-C02 では第2分野「新しいソリューションのための設計」と第3分野「既存のソリューションの継続的な改善」に相当します。
> **目安時間**: 読む 6.5時間 / 確認問題と復習 2.5時間

> [!NOTE]
> SQS / SNS / EventBridge / Kinesis の基本は [アプリケーション統合](../02-associate/09-application-integration.md)、Lambda / API Gateway / Step Functions の基本は [サーバーレス](../02-associate/10-serverless.md)、ECS / EKS / Fargate / ECR の基本は [コンテナ](../02-associate/11-containers.md) で学習済みとして進めます。本章は「複数のサービスとチームにまたがるシステムを、どう組み合わせて設計するか」という SAP の視点で扱います。

## この章の全体像

クラウドネイティブな設計とは、クラウドの上で動かすことではなく、**クラウドの性質（弾力性、マネージドサービス、従量課金、API による自動化）を前提に設計すること** です。代表的な構成は次のようになります。

## 1. クラウドネイティブの原則

### 1.1 原則と設計への落とし込み

| 原則 | 意味 | 設計の例 | AWS の主な手段 |
|---|---|---|---|
| 障害を前提に設計する | 部品は必ず壊れる。壊れても全体は止めない | マルチ AZ、タイムアウトとリトライ、障害の隔離 | ELB、Auto Scaling、SQS、ARC |
| 疎結合 | 相手の障害・遅延・変更を波及させない | 非同期メッセージング、イベント、API の契約 | SQS、SNS、EventBridge、API Gateway |
| マネージドサービスを優先する | 差別化にならない運用は AWS に任せる | サーバーレス、マネージド DB | Lambda、Fargate、DynamoDB、Aurora |
| 計算はステートレスに、状態は外へ | どのインスタンスでも要求を処理できる | セッション・ファイルを外部に置く | DynamoDB、ElastiCache、S3 |
| すべてを自動化する | 手作業の変更をなくす | IaC、CI/CD、自動修復 | CloudFormation、AWS CDK、CodePipeline |
| 不変のインフラストラクチャ | 変更は修正ではなく置き換えで行う | イメージの入れ替え、ブルー/グリーンデプロイ | ECR、EC2 Image Builder、ECS の組み込みブルー/グリーン |
| 可観測性を組み込む | 外から内部の状態を推測できる | 構造化ログ、分散トレース、SLO | CloudWatch、X-Ray、Application Signals |
| 最小権限とゼロトラスト | ネットワークの内側でも無条件に信頼しない | サービスごとの IAM ロール、サービス間の認証 | IAM、VPC Lattice の認証ポリシー |
| 使った分だけ払う | 需要に合わせて伸縮する | ゼロまでスケール、スポット、Graviton | Lambda、Fargate Spot、Aurora Serverless v2 |

### 1.2 分散システムのコストを理解する

マイクロサービスは目的ではなく手段です。サービスを分けると、独立したデプロイとスケーリングが得られる一方で、次のコストを払うことになります。

- ネットワーク越しの呼び出しは失敗し、遅延が積み重なります。
- サービスをまたぐデータは結果整合性になり、分散トランザクションの扱いが必要になります（4.4 節、9 節）。
- 障害の調査には、分散トレースと相関 ID が欠かせません。

チームが小さく、変更の頻度も高くないなら、モジュールの境界をはっきりさせた **モジュラーモノリス** から始めるのも合理的な選択です。サービスの境界は、チームの境界（コンウェイの法則）と業務のまとまり（境界づけられたコンテキスト）に合わせます。

### 1.3 実行基盤の選び方

| 観点 | Lambda | コンテナ（ECS / EKS、Fargate） | EC2 |
|---|---|---|---|
| 実行時間 | 1 回の呼び出しは最大 15 分 | 制限なし | 制限なし |
| スケール | 要求に応じて自動（ゼロまで） | タスク / Pod 単位で自動 | インスタンス単位 |
| 運用の手間 | 最小 | 中（イメージ、クラスター） | 大 |
| 向く処理 | イベント駆動、断続的、短時間 | 常時稼働の API、長時間の処理、移植性 | 特殊な OS・ハードウェア、ライセンスの制約 |
| 料金の基準 | 要求数と実行時間 | vCPU とメモリの時間 | インスタンスの時間 |

大量で安定した負荷の Lambda には、**Lambda Managed Instances**（2025年11月）という選択肢もあります。自分のアカウントの EC2 インスタンス上で Lambda 関数を動かし、Savings Plans やリザーブドインスタンスを適用できます。

> [!TIP]
> **試験のポイント**: 「運用上のオーバーヘッドを最小に」「断続的な負荷」→ サーバーレス（Lambda、Fargate、DynamoDB）。「15 分を超える処理」→ Lambda 単体ではなく、コンテナ、Step Functions、または Lambda durable functions（4.7 節）。「特定のインスタンスタイプや GPU が必要」→ EC2 系（ECS Managed Instances、EKS のノード）。

## 2. イベント駆動アーキテクチャ

### 2.1 なぜイベント駆動にするのか

イベントとは「注文が確定した」のような **過去に起きた事実** です。発行側はイベントを出すだけで、誰がどう使うかを知りません。この性質から、次の利点が生まれます。

- **時間的な分離**: 受け取り側が停止していても、発行側は処理を続けられます。
- **独立したスケーリング**: 発行側と受け取り側は、それぞれの負荷に合わせて伸縮します。
- **拡張のしやすさ**: 新しい受け取り側を追加しても、発行側のコードは変わりません。
- **監査と再処理**: イベントを保存しておけば、後から再生して状態を作り直せます。

| 種類 | 意味 | 例 | 結合の強さ |
|---|---|---|---|
| コマンド | 相手に何かをさせる依頼 | 「在庫を引き当てよ」 | 強い（相手を知っている） |
| イベント（通知型） | 事実と ID だけを伝える | 「注文 123 が確定した」 | 弱い（詳細は受け取り側が問い合わせる） |
| イベント（状態転送型） | 事実と必要なデータを含めて伝える | 「注文 123 が確定した（商品・金額・配送先）」 | 弱い（受け取り側は問い合わせ不要） |

### 2.2 EventBridge を中心にした設計

Amazon EventBridge は、イベントを **ルールで振り分ける** サーバーレスのイベントバスです。

| 機能 | 内容 | 設計での使いどころ |
|---|---|---|
| イベントバス | 既定（AWS サービスのイベント）、カスタム、パートナー（SaaS） | ドメインごと、または組織の中央にカスタムバスを置く |
| ルール | イベントパターン（プレフィックス、数値の範囲、存在の有無、anything-but など）で絞り込み、ターゲットへ送る。1 つのルールにターゲットは最大 5 つ | 受け取り側ごとにルールを分け、独立して追加・削除する |
| 入力トランスフォーマー | ターゲットに渡す内容を加工する | 受け取り側の API の形式に合わせる |
| アーカイブと再生 | イベントを保存し、後から再送する | 障害からの復旧、新しい受け取り側のための過去データの投入 |
| スキーマレジストリ | イベントの構造を登録・検出し、コードのひな形を生成する | チーム間のイベントの契約 |
| EventBridge Pipes | ソース（SQS、Kinesis、DynamoDB Streams など）→ フィルター → 加工 → ターゲットを 1 対 1 でつなぐ | 変更データのイベント化（9.4 節）、つなぎのコードの削減 |
| EventBridge Scheduler | 1 回限り・定期のスケジュール実行 | cron サーバーの置き換え |

押さえるべき性質は次のとおりです。

- **配信は少なくとも 1 回** で、**順序は保証されません**。受け取り側は冪等にします（4.6 節）。順序が必要なら SQS FIFO や Kinesis Data Streams を使います。
- ターゲットへの送信に失敗すると、既定で **最大 24 時間・185 回** まで再試行します。再試行しきれなかったイベントは、ターゲットごとの DLQ（SQS）に送れます。
- イベントの最大サイズは **1 MB** です（2026年9月時点）。試験や古い教材では 256 KB として出題される可能性があります。大きなデータは S3 に置き、イベントには参照だけを入れます（クレームチェックパターン）。

### 2.3 マルチアカウント・マルチリージョンのイベントルーティング

大規模な組織では、アカウントをまたいでイベントを流します。

```mermaid
flowchart LR
    subgraph PROD["発行側アカウント（注文）"]
        APP["注文サービス"] --> LBUS["ローカルの<br/>イベントバス"]
    end
    subgraph HUB["イベントハブのアカウント"]
        CBUS["中央の<br/>カスタムイベントバス"]
        ARC["アーカイブ"]
    end
    subgraph CONS1["受け取り側アカウント（配送）"]
        B1["イベントバス"] --> T1["Step Functions"]
    end
    subgraph CONS2["受け取り側アカウント（分析）"]
        B2["イベントバス"] --> T2["Data Firehose"]
    end
    LBUS -- "ルール: 他アカウントの<br/>バスをターゲットに" --> CBUS
    CBUS --> ARC
    CBUS -- "ルール" --> B1
    CBUS -- "ルール" --> B2
```

- 他のアカウントのイベントバスをルールのターゲットにできます。受信側のバスには、送信元を許可するリソースベースのポリシーを設定します。組織全体を許可するには `aws:PrincipalOrgID` 条件を使います。
- 他のリージョンのイベントバスもターゲットにできます。
- **グローバルエンドポイント** を使うと、プライマリのリージョンのバスに障害が起きたときに、Route 53 のヘルスチェックに基づいてセカンダリのリージョンへイベントの受け付けを切り替えられます。

中央のハブを置く構成は、ルーティングとアーカイブを一元管理できる一方で、ハブのチームがボトルネックになりがちです。ドメインごとにバスを持ち、必要なイベントだけを他のドメインへ流す構成と、組織の規模に応じて使い分けます。

### 2.4 コレオグラフィとオーケストレーション

複数のサービスで業務を進める方法は、大きく 2 つあります。

```mermaid
flowchart TB
    subgraph CHO["コレオグラフィ（EventBridge）"]
        O1["注文サービス"] -- "OrderPlaced" --> BUS1["イベントバス"]
        BUS1 --> PAY1["決済サービス"]
        BUS1 --> INV1["在庫サービス"]
        BUS1 --> NTF1["通知サービス"]
        PAY1 -- "PaymentCompleted" --> BUS1
    end
    subgraph ORC["オーケストレーション（Step Functions）"]
        SM["注文ワークフロー"] -- "1" --> PAY2["決済"]
        SM -- "2" --> INV2["在庫の引き当て"]
        SM -- "3" --> SHP2["出荷の指示"]
    end
```

| 観点 | コレオグラフィ | オーケストレーション |
|---|---|---|
| 制御の方法 | 各サービスがイベントに反応して自律的に動く | 中央のワークフローが順序と分岐を指示する |
| 結合度 | 最も弱い。発行側は受け取り側を知らない | ワークフローが各サービスの API を知っている |
| 全体の流れの把握 | 難しい（流れが各サービスに分散） | 容易（ワークフローの定義と実行履歴で見える） |
| エラー処理・補償 | 各サービスに分散して実装する | ワークフローで一元的に扱える（Retry / Catch、Saga） |
| 変更のしやすさ | 受け取り側の追加が容易 | 流れの変更はワークフローの変更で済む |
| 向く処理 | 独立した多数の反応（通知、分析、キャッシュ更新） | 順序・条件・期限・補償が重要な業務プロセス（注文、承認、決済） |

実務では **両方を組み合わせます**。ドメインの中の手順はオーケストレーション（Step Functions）で確実に進め、ドメインの間はイベント（EventBridge）で疎に結ぶのが定石です。

> [!TIP]
> **試験のポイント**: 「多数のチームのシステムが、発行側を変えずに同じ出来事へ反応できるようにしたい」→ EventBridge のカスタムバスとルール（コレオグラフィ）。「複数の手順を順序どおりに実行し、失敗時に補償したい」「処理の状態を可視化したい」→ Step Functions（オーケストレーション）。「SaaS のイベントを取り込みたい」→ パートナーイベントバス。

> [!WARNING]
> **ひっかけ注意**: 1 つの SQS キューを複数の受け取り側で共有すると、各メッセージは **どれか 1 つの受け取り側だけ** が処理します（競合コンシューマー）。全員に届けたいなら、SNS や EventBridge でファンアウトし、受け取り側ごとにキューを用意します。また、EventBridge は順序を保証しないため、「順序どおりに処理」が要件なら SQS FIFO や Kinesis Data Streams を選びます。

### 2.5 イベント設計のベストプラクティス

- **封筒（エンベロープ）をそろえる**: `source`、`detail-type`、`detail` の中にイベント ID、発生時刻、スキーマのバージョン、相関 ID を入れます。
- **スキーマは後方互換で進化させる**: フィールドの追加は許し、削除や意味の変更は新しいバージョン（新しい `detail-type`）として出します。
- **受け取り側を冪等にする**: 少なくとも 1 回の配信なので、同じイベントが 2 回届いても結果が変わらないようにします（4.6 節）。
- **失敗を隔離する**: ターゲットごとに DLQ を設定し、再処理（リドライブ）の手順を決めておきます。
- **追跡できるようにする**: 相関 ID とトレースのコンテキストを引き継ぎ、分散トレースでイベントの流れを追えるようにします。

| 要件 | 選ぶサービス |
|---|---|
| ルールによる柔軟な振り分け、AWS サービスや SaaS のイベント、スキーマの管理 | EventBridge |
| 大量の購読者への単純なファンアウト、メール・SMS・モバイル通知 | SNS（順序が必要なら SNS FIFO） |
| 1 つの処理側へのバッファリング、負荷平準化、再試行 | SQS |
| 順序付きの大量のストリーム、複数の処理側による保持期間内の再読み込み | Kinesis Data Streams |
| Apache Kafka との互換性が必要 | Amazon MSK |

## 3. サーバーレスデータパイプライン

データパイプラインをサーバーレスで組むと、クラスターの運用が不要になり、データ量に応じて自動で伸縮し、処理した分だけ支払えます。さらに、定時のポーリングではなく **データの到着をきっかけに処理を始める** ため、遅延も小さくなります。

```mermaid
flowchart LR
    subgraph BATCH["ファイル到着型"]
        S3IN["S3<br/>（取り込み用）"] -- "Object Created" --> EBR["EventBridge"]
        EBR --> SFNB["Step Functions<br/>（検証 → 変換 → 登録）"]
        SFNB --> GLUE["AWS Glue ジョブ<br/>/ Lambda"]
    end
    subgraph STREAM["ストリーミング"]
        PRD["アプリ / IoT"] --> KDS["Kinesis Data Streams"]
        KDS --> LMB["Lambda<br/>（リアルタイム処理）"]
        KDS --> FH["Data Firehose<br/>（バッファリング・形式変換）"]
    end
    GLUE --> S3OUT["S3<br/>（Parquet / Iceberg）"]
    FH --> S3OUT
    S3OUT --> CAT["Glue Data Catalog"] --> ATH["Athena / Redshift"]
```

### 3.1 代表的なパターン

| パターン | 流れ | 向くケース |
|---|---|---|
| ファイル到着型 | S3 → EventBridge → Step Functions → Glue / Lambda → S3（Parquet / Iceberg）→ Glue Data Catalog | 取引先からのファイル、日次の取り込み |
| ストリーミング | Kinesis Data Streams → Lambda / Managed Service for Apache Flink → Data Firehose → S3 | ログ、IoT、クリックストリーム |
| 変更データ（CDC） | DynamoDB Streams / DMS → EventBridge Pipes / Kinesis → 変換 → 分析用のストア | 業務 DB の変更を分析や他のサービスへ届ける |
| 大量オブジェクトの一括処理 | Step Functions の Distributed Map → Lambda / Express ワークフロー | 数百万ファイルの変換・検証（4.2 節） |
| 定期実行 | EventBridge Scheduler → Step Functions | 集計、レポートの作成 |

変換の処理には、データ量と処理の性質に合ったサービスを選びます。

| 処理 | 選択肢 | 目安 |
|---|---|---|
| 小さな変換・検証 | Lambda | 1 回 15 分まで、メモリは最大 10,240 MB |
| 大規模な ETL（Spark） | AWS Glue、Amazon EMR Serverless | 大容量のデータの結合・集計 |
| SQL で書ける変換 | Amazon Athena（CTAS、INSERT INTO） | 分析者が SQL のまま保守できる |
| 状態を持つストリーム処理 | Amazon Managed Service for Apache Flink | ウィンドウ集計、異常検知 |
| コンテナによる長時間の処理 | Fargate、AWS Batch | 既存のコンテナ化されたジョブ |

### 3.2 設計のポイント

| 論点 | 起きる問題 | 対策 |
|---|---|---|
| 再処理と重複 | リトライや再実行で同じデータが二重に書き込まれる | 冪等な書き込み（パーティション単位の上書き、Iceberg の MERGE による upsert、イベント ID での重複排除） |
| 失敗の隔離 | 1 件の不正データでバッチ全体が止まる | DLQ、失敗時の送信先、Kinesis のイベントソースマッピングのバッチ分割（BisectBatchOnFunctionError）と部分的なバッチ応答、Step Functions の Catch |
| 背圧（下流の処理能力の不足） | 下流の DB や API が過負荷になる | SQS でバッファリング、SQS のイベントソースマッピングの最大同時実行数、Lambda の予約済み同時実行 |
| 小さなファイル | 大量の小さなファイルで分析が遅くなる | Firehose のバッファリング、Iceberg テーブルの定期的なコンパクション |
| スキーマの変化 | 項目の追加で下流が壊れる | Glue Schema Registry、Iceberg のスキーマ進化 |
| データ品質 | 不正なデータが分析に混ざる | AWS Glue Data Quality のルールで検証し、不合格のデータを隔離 |
| オーケストレーション | 手順・依存関係・再試行の管理 | Step Functions（AWS サービスとの直接統合）、EventBridge Scheduler、Amazon MWAA（Airflow の DAG が既にある場合） |

> [!WARNING]
> **ひっかけ注意**: 古い問題では、定期的な ETL の答えとして **AWS Data Pipeline** が登場します。Data Pipeline は新規受付を終了しており、新しい設計では Step Functions、AWS Glue（ワークフロー、トリガー）、Amazon MWAA を使います。

> [!TIP]
> **試験のポイント**: 「ファイルの到着をきっかけに、サーバーを管理せずに処理」→ S3 のイベント → EventBridge → Step Functions / Lambda。「ストリームを S3 に取り込み、形式を Parquet に変換」→ Data Firehose。「1 件の不正レコードで処理全体を止めたくない」→ 部分的なバッチ応答、DLQ、バッチの分割。レイクハウス（Iceberg、Lake Formation）の設計は [データと分析のアーキテクチャ](10-data-analytics-architecture.md) で扱います。

## 4. 耐久性のあるワークフロー

### 4.1 耐久性のあるワークフローと Standard / Express

注文処理、審査、データの移行のように、数分から数か月にわたり、多数の手順を踏む処理があります。途中で障害が起きても、**完了した手順をやり直さずに続きから再開できる** ことを「耐久性がある（durable）」と言います。そのためには、各手順の結果と現在の状態を、処理の外に確実に保存しておく必要があります。

AWS Step Functions は、この状態管理を AWS が引き受けるワークフローのサービスです。2 種類のワークフローがあります。

| 観点 | Standard | Express |
|---|---|---|
| 最長の実行時間 | 1 年 | 5 分 |
| 実行のセマンティクス | ワークフローの実行は正確に 1 回（exactly-once） | 非同期: 少なくとも 1 回 / 同期: 最大 1 回 |
| 料金の基準 | 状態遷移の回数 | 実行回数と実行時間（使用メモリ量に応じる） |
| 実行履歴 | コンソールと API で確認できる（終了後 90 日間） | CloudWatch Logs に出力する（ログの設定が必要） |
| ジョブの完了待ち（.sync）とコールバック（.waitForTaskToken） | 対応 | 非対応 |
| 失敗したステートからの再開（redrive） | 対応 | 非対応 |
| 向く処理 | 長時間の業務プロセス、人の承認、監査が必要な処理 | 大量・短時間のイベント処理、ストリームの変換、API のバックエンド |

> [!TIP]
> **試験のポイント**: 「最大で数日〜数か月」「人の承認を待つ」「実行の履歴を監査に使う」→ Standard。「毎秒大量の短い処理」「最もコスト効率よく」「5 分以内に終わる」→ Express。Express でコールバック（タスクトークン）を待つ選択肢は誤りです。

### 4.2 Distributed Map による大規模な並列処理

Map ステートには 2 つのモードがあります。

- **インライン Map**: 同じ実行の中で要素を並列に処理します。同時実行は最大 40 で、すべての処理が 1 つの実行履歴に記録されます（1 つの実行履歴のイベント数には 25,000 の上限があります）。数十〜数百件の処理に向きます。
- **Distributed Map**: 要素（またはまとめた要素のバッチ）ごとに **子ワークフローの実行** を起動します。最大 10,000 の子ワークフローを並列に実行でき、それぞれが独自の実行履歴を持ちます。

Distributed Map の主な設定は次のとおりです。

| 設定 | 内容 |
|---|---|
| 項目の読み込み（ItemReader） | S3 の CSV・JSON、S3 インベントリのマニフェスト、プレフィックス配下のオブジェクト一覧などから処理対象を読む |
| バッチ化（ItemBatcher） | 複数の要素をまとめて 1 つの子ワークフローに渡し、起動回数とコストを減らす |
| 最大同時実行数（MaxConcurrency） | 下流の DB や API を守るために並列度を制限する |
| 許容する失敗（ToleratedFailurePercentage / Count） | 一定の割合・件数までの失敗なら全体を成功とみなす |
| 結果の書き出し（ResultWriter） | 子ワークフローの結果を S3 に書き出す（失敗した要素の特定と再処理に使う） |
| 子ワークフローの種類 | 短い処理なら Express（安価）、長い処理や完了待ちが必要なら Standard |

### 4.3 エラー処理

Step Functions では、エラー処理をワークフローの定義として宣言します。

```json
{
  "ChargePayment": {
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "charge-payment",
      "Payload": {
        "orderId.$": "$.orderId",
        "idempotencyKey.$": "$.orderId"
      }
    },
    "TimeoutSeconds": 30,
    "Retry": [
      {
        "ErrorEquals": ["Lambda.ServiceException", "Lambda.TooManyRequestsException", "States.Timeout"],
        "IntervalSeconds": 2,
        "BackoffRate": 2.0,
        "MaxAttempts": 5,
        "MaxDelaySeconds": 60,
        "JitterStrategy": "FULL"
      }
    ],
    "Catch": [
      {
        "ErrorEquals": ["PaymentDeclined"],
        "ResultPath": "$.error",
        "Next": "ReleaseInventory"
      }
    ],
    "Next": "ArrangeShipping"
  }
}
```

- **Retry**: エラーの種類ごとに、間隔（IntervalSeconds）、倍率（BackoffRate）、回数（MaxAttempts）、待ち時間の上限（MaxDelaySeconds）、ジッター（JitterStrategy）を指定します。一時的なエラーだけを再試行し、業務エラー（カード決済の拒否など）は再試行しません。
- **Catch**: 再試行しても失敗したとき、またはすぐに扱うべき業務エラーのときに、補償や通知などの別のステートへ進めます。`ResultPath` でエラー情報を入力に残しておくと、後続の処理で原因を使えます。
- **タイムアウト**: `TimeoutSeconds`（ステート全体）と `HeartbeatSeconds`（コールバックやアクティビティの生存確認）を明示的に設定し、応答のない処理を待ち続けないようにします。
- **redrive**: Standard ワークフローが失敗した場合、原因を直したあとで **失敗したステートから再開** できます。成功済みのステートはやり直しません。

### 4.4 Saga パターンと補償

マイクロサービスでは、サービスごとに DB が分かれているため、複数のサービスにまたがる処理を 1 つの DB トランザクションで囲めません。**Saga パターン** は、各サービスのローカルなトランザクションを順に実行し、途中で失敗したら、完了済みの手順を **補償トランザクション**（逆の業務操作）で打ち消す方法です。

```mermaid
flowchart LR
    ST(["開始"]) --> R["在庫を引き当てる"]
    R --> P["決済する"]
    P --> SH["出荷を手配する"]
    SH --> DONE(["完了"])
    R -. "失敗" .-> FAIL(["注文失敗として終了"])
    P -. "失敗（Catch）" .-> CR["補償: 在庫の<br/>引き当てを解除"]
    SH -. "失敗（Catch）" .-> CP["補償: 決済を返金"]
    CP --> CR
    CR --> FAIL
```

設計のポイントは次のとおりです。

- **補償は「取り消し」ではなく「逆の業務操作」**: 決済の補償は返金、在庫の引き当ての補償は解除です。DB のロールバックとは異なり、返金の記録のように履歴が残ります。
- **補償は逆順に、冪等に、再試行可能に**: 補償も失敗しうるため Retry を付け、それでも失敗したら人が対応するキューへ送ります。
- **途中の状態が他から見える**: 「仮引き当て」「決済処理中」などの状態を定義し、他の処理がそれを前提に動けるようにします（結果整合性）。
- **後戻りできない手順を意識する**: 出荷のように取り消せない手順の後は、補償ではなく前進（再試行や代替手段）で回復するように順序を設計します。

Step Functions でオーケストレーションすると、補償の流れを Catch で一元的に表現でき、どの手順で失敗して何を補償したかが実行履歴に残ります。コレオグラフィ（イベント）でも Saga は実装できますが、流れが分散するため、手順の多い業務ではオーケストレーションのほうが保守しやすくなります。

### 4.5 タスクトークンによる人の承認

人の承認や外部システムの応答を待つには、**コールバック（.waitForTaskToken）** の統合パターンを使います。

```mermaid
sequenceDiagram
    participant SFN as Step Functions（Standard）
    participant L as Lambda（承認依頼の送信）
    participant APR as 承認者
    participant API as API Gateway + Lambda
    SFN->>L: タスクトークンを渡して呼び出す
    L->>APR: 承認依頼を送信（トークンを保存し参照を通知）
    Note over SFN: 実行は一時停止（HeartbeatSeconds / TimeoutSeconds で上限を制御）
    APR->>API: 承認または却下（認証付き）
    API->>SFN: SendTaskSuccess または SendTaskFailure
    SFN->>SFN: 承認なら次へ、却下やタイムアウトなら Catch で分岐
```

- タスクの定義で `.waitForTaskToken` を付け、コンテキストオブジェクトの `$$.Task.Token` を Lambda、SQS、SNS などへ渡します。
- 実行は、トークンを指定した `SendTaskSuccess` / `SendTaskFailure` が呼ばれるまで一時停止します。待機中にコンピューティングは動いていません。
- `TimeoutSeconds` を過ぎると `States.Timeout` になり、Catch でエスカレーション（上長への再依頼など）へ進めます。
- タスクトークンは、実行を進められる「鍵」です。承認の API は認証を付け、トークンそのものを公開された URL にそのまま載せないようにします。
- この統合パターンは Standard ワークフローでのみ使えます。

### 4.6 冪等性

分散システムでは、「少なくとも 1 回」の配信、リトライ、再実行によって、**同じ処理が 2 回以上実行されることを前提に** 設計します。冪等（何回実行しても結果が同じ）にしておけば、重複は害になりません。

| 重複が起きる場所 | 例 | 対策 |
|---|---|---|
| クライアントの再送 | タイムアウト後の再送で、同じ注文が 2 回登録される | クライアントが作った冪等性キー（リクエスト ID）を受け取り、DynamoDB の条件付き書き込み（`attribute_not_exists`）で初回だけ処理する |
| メッセージの重複配信 | SQS 標準キュー、SNS、EventBridge は少なくとも 1 回の配信 | 処理済みのイベント ID を記録する。処理自体を upsert や絶対値の設定にする |
| ワークフローのリトライ・redrive | 決済の API 呼び出しが 2 回行われる | 外部の API に冪等性キー（注文 ID など）を渡す |
| ワークフローの二重起動 | 同じイベントで 2 回 StartExecution が呼ばれる | Standard ワークフローの実行名に業務キーを使う（同じ実行名では 90 日間、新しい実行を開始できない） |
| FIFO キューへの再送 | 送信側の再送 | SQS FIFO の重複排除 ID（5 分間の重複排除） |

冪等性キーの実装では、「処理中」と「完了」の状態を分けて記録し（同時に届いた重複を防ぐ）、完了時には結果も保存して、重複した要求に同じ応答を返します。記録には DynamoDB の TTL で有効期限を付けます。Lambda では、Powertools for AWS Lambda の冪等性ユーティリティがこの仕組みを提供しています。

### 4.7 Lambda durable functions との使い分け

**Lambda durable functions**（2025年12月に一般提供開始）は、複数の手順からなる処理を、ワークフローの定義ではなく **Lambda 関数のコードとして** 書ける機能です。

- コードの中で「ステップ（step）」「待機（wait）」「コールバック（外部からの応答待ち）」「他の Lambda 関数の呼び出し」を、SDK の耐久性のある操作として書きます。各操作の入力と結果は、実行の履歴として記録されます。
- 障害や待機からの再開時には、関数を先頭から再実行（リプレイ）しますが、完了済みのステップは記録済みの結果を返すため、やり直しません（チェックポイントとリプレイ）。そのため、ステップの外に乱数や現在時刻のような「実行のたびに変わる処理」を書かないことが重要です。
- 待機やコールバックで実行を中断し、**最大 1 年** まで待てます。待機中はコンピューティングの料金がかかりません。1 回の Lambda 呼び出しの上限（15 分）を超える処理を、コードのまま書けるのが大きな特徴です。

| 観点 | Step Functions | Lambda durable functions |
|---|---|---|
| 定義の方法 | Amazon States Language（JSON / YAML）、Workflow Studio で視覚的に | Lambda 関数のコード（対応ランタイムの SDK） |
| AWS サービスとの統合 | 多数のサービスをコードなしで直接呼び出せる（.sync、タスクトークンを含む） | コードから AWS SDK で呼び出す |
| 流れの可視化 | ステートの図と実行履歴で、開発者以外にも見える | 操作の履歴として記録される。流れはコードを読んで把握する |
| 最長の実行 | Standard は 1 年、Express は 5 分 | 最大 1 年 |
| 大規模な並列処理 | Distributed Map（最大 10,000 の子ワークフロー） | コードで記述する |
| 向く場面 | 複数のサービスやチームをまたぐ業務プロセス、運用担当者も流れを追いたい、ローコードで統合したい | アプリの開発チームがロジックをコードで完結させたい、テストをコードで書きたい、AI エージェントの多段処理 |

使い分けの目安は、「**流れそのものを組織で共有・監査したいか**」と「**ロジックがアプリのコードに閉じているか**」です。多数の AWS サービスをつなぐ業務プロセスや大規模な並列処理は Step Functions、アプリ内の多段処理を開発者がコードで管理したいなら durable functions が向きます。両者は組み合わせることもでき、Step Functions のワークフローの 1 つの手順として durable functions を呼び出す構成も取れます。

> [!NOTE]
> SAP-C03 の発表では「Step Functions による耐久性のあるワークフロー」が明示されています。Step Functions の Standard / Express、Distributed Map、エラー処理、Saga、タスクトークンを確実に押さえたうえで、durable functions は「コード中心で長時間の処理を書く新しい選択肢」として理解しておきましょう。

## 5. マイクロサービス間の通信

### 5.1 同期と非同期

| 観点 | 同期（HTTP / gRPC） | 非同期（キュー、イベント） |
|---|---|---|
| 結果の受け取り | その場で結果が必要な処理に向く | 結果は後で受け取る |
| 呼び出し先の障害 | 呼び出し元も失敗する | メッセージが溜まり、復旧後に処理される |
| 遅延 | 呼び出しの連鎖で積み重なる | 呼び出し元はすぐに応答できる |
| 障害への備え | タイムアウト、リトライ、サーキットブレーカー | DLQ、冪等性、再処理 |
| 例 | 在庫の照会、価格の計算 | 注文確定後の通知、ポイントの付与 |

同期呼び出しの連鎖は、可用性を掛け算で下げます。可用性 99.9% のサービスを 5 つ直列に呼ぶと、全体は 0.999⁵ ≈ **99.5%** になり、年間の停止時間の目安は約 9 時間から約 44 時間に増えます。「その場で結果が必要か」を問い、不要な部分は非同期にするのが基本です。

### 5.2 サービスの検出と App Mesh の終了

**AWS Cloud Map** は、サービスの名前と場所（IP アドレス、ポート、属性）を登録し、DNS または API（DiscoverInstances）で検出できるようにするサービスです。ECS のサービス検出と ECS Service Connect は Cloud Map の名前空間を使います。EKS では Kubernetes の Service と CoreDNS が同じ役割を担います。

検出だけでは、リトライ、暗号化、認可、メトリクスは得られません。これらをアプリの外で提供するのがサービスメッシュで、AWS では **AWS App Mesh**（Envoy のサイドカーを利用者が管理する方式）が使われてきました。App Mesh は 2024年9月に新規受付を終了し、**2026年9月30日にサポート終了** です（[サポート終了が発表されたサービスの一覧](https://docs.aws.amazon.com/general/latest/gr/sunset_services.html)）。

| 現在の構成 | 移行先 | 理由 |
|---|---|---|
| ECS のサービス同士の通信 | **ECS Service Connect** | ECS に統合されており、プロキシを利用者が管理する必要がない |
| EKS、または ECS・EKS・EC2・Lambda の混在 | **Amazon VPC Lattice**（EKS は AWS Gateway API Controller で統合） | サイドカーが不要で、コンピューティングの種類を問わない |
| VPC・アカウントをまたぐ通信、IAM による認可 | **Amazon VPC Lattice** | サービスネットワークを RAM で共有し、認証ポリシーで認可できる |
| 高度な mTLS やトラフィック制御が必須で、自社で運用できる | EKS 上の Istio などのオープンソースのメッシュ | 機能は豊富だが、運用の負荷が大きい |

> [!WARNING]
> **ひっかけ注意**: 試験の選択肢に App Mesh が登場しても、新規の設計では選びません。「サービスメッシュ」「サービス間のトラフィック制御」という言葉があれば、ECS なら Service Connect、アカウントや VPC、コンピューティングの種類をまたぐなら VPC Lattice を考えます。

### 5.3 ECS Service Connect

```mermaid
flowchart LR
    subgraph NS["Service Connect の名前空間（Cloud Map）"]
        subgraph TA["注文サービスのタスク"]
            A1["アプリ"] --> P1["Service Connect<br/>プロキシ"]
        end
        subgraph TB["在庫サービスのタスク"]
            P2["Service Connect<br/>プロキシ"] --> A2["アプリ"]
        end
    end
    P1 -- "http://inventory:8080<br/>（負荷分散・リトライ・メトリクス）" --> P2
```

- ECS がタスクにプロキシを追加して管理します。アプリは `http://inventory:8080` のような短い名前で相手を呼ぶだけです。
- 負荷分散、リトライ、外れ値の検出（異常なタスクを一時的に外す）、接続のドレインを提供し、サービスごとのリクエスト数・エラー・遅延を CloudWatch のメトリクスとして出します。
- AWS Private CA の証明書を使って、サービス間の通信を TLS で暗号化できます。
- 2026年7月には、同じ AZ のタスクを優先して呼ぶゾーン認識ルーティングが追加され、AZ 間の遅延とデータ転送料金を抑えられるようになりました。
- 対象は ECS のサービスです。EKS や Lambda との通信には VPC Lattice を組み合わせます。

### 5.4 Amazon VPC Lattice

```mermaid
flowchart LR
    subgraph ACCA["アカウント A（VPC 1）"]
        C1["クライアント<br/>（ECS のタスク）"]
    end
    subgraph ACCB["アカウント B（VPC 2、CIDR 重複可）"]
        C2["クライアント<br/>（EKS の Pod）"]
    end
    SN["VPC Lattice<br/>サービスネットワーク<br/>（認証ポリシー）"]
    subgraph ACCC["アカウント C"]
        SVC1["注文サービス<br/>（ECS）"]
        SVC2["決済サービス<br/>（Lambda）"]
        RDB[("DB<br/>（リソース設定・TCP）")]
    end
    C1 --> SN
    C2 --> SN
    SN --> SVC1
    SN --> SVC2
    SN --> RDB
```

- **サービスネットワーク** という論理的な境界に、サービスと VPC を関連付けます。関連付けた VPC のクライアントは、VPC ピアリングや Transit Gateway なしでサービスを呼べます。VPC の CIDR が重複していても構いません。
- **サービス** はリスナー、ルール（パス、ヘッダー、メソッドによる振り分け、加重ルーティング）、ターゲットグループで構成します。ターゲットには EC2 インスタンス、IP アドレス、Lambda 関数、ALB、ECS のサービス、EKS の Pod（AWS Gateway API Controller）を使えます。
- **認証ポリシー** を、サービスネットワークとサービスの両方に設定できます。SigV4 で署名された要求を IAM で認可するため、「どのサービス（IAM ロール）がどの API を呼べるか」を宣言的に管理できます。
- サービスネットワークは AWS RAM でアカウント間に共有できます。**リソース設定** と **リソースゲートウェイ** を使えば、DB のような TCP のリソースも公開できます。ネットワーク側の詳細は [高度なネットワーク設計](04-advanced-networking.md) を参照してください。

### 5.5 比較

| 観点 | ECS Service Connect | Amazon VPC Lattice | Cloud Map（検出のみ） | AWS App Mesh 【サポート終了】 |
|---|---|---|---|---|
| 対象 | ECS のサービス同士 | EC2、ECS、EKS、Lambda、IP、TCP のリソース | 任意 | ECS、EKS、EC2 |
| 仕組み | ECS が管理するプロキシをタスクに追加 | VPC に組み込まれたマネージドなアプリケーション層のネットワーク（サイドカー不要） | 名前解決のみ | 利用者が管理する Envoy のサイドカー |
| VPC・アカウントをまたぐ通信 | 同じ名前空間の ECS サービスが中心 | サービスネットワークで複数の VPC・アカウントを接続（CIDR の重複可） | ネットワーク接続は別途必要 | ネットワーク接続は別途必要 |
| 暗号化・認可 | TLS（AWS Private CA） | TLS、IAM の認証ポリシー（SigV4） | なし | mTLS など |
| トラフィック制御 | リトライ、外れ値の検出、タイムアウト | パス・ヘッダーによる振り分け、加重ルーティング | なし | 豊富 |
| 状況（2026年9月時点） | 利用可能 | 利用可能 | 利用可能 | 2026年9月30日にサポート終了 |

### 5.6 同期呼び出しの回復性パターン

- **タイムアウト**: すべての呼び出しに設定します。下流ほど短くし、呼び出し元より先に呼び出し先がタイムアウトするようにします。
- **リトライ**: 一時的なエラーだけを、指数バックオフとジッターで、回数に上限を付けて再試行します。リトライの嵐で障害を悪化させないよう、全体の再試行の割合にも上限（リトライ予算）を設けます。再試行するのは冪等な操作だけです。
- **サーキットブレーカー**: 失敗が続いたら呼び出しを一時的に止め、すぐにエラーやフォールバックを返します。
- **バルクヘッド**: 呼び出し先ごとに接続プールやスレッドを分け、1 つの遅い依存先がすべての処理能力を使い切らないようにします。
- **フォールバックと縮退運転**: キャッシュの値や既定値で応答し、機能を絞ってでもサービスを続けます。
- **負荷制限**: 処理しきれない要求は早めに断り（API Gateway のスロットリングなど）、重要な要求を優先します。

回復性の設計と検証（FIS による障害注入など）は [回復力と事業継続](06-resilience-business-continuity.md) で扱います。

## 6. フロントドア: API Gateway / AppSync / ALB

外部からの要求を受ける「入口」は、プロトコル、認証、流量制御、キャッシュ、料金の違いで選びます。

| 観点 | Amazon API Gateway | AWS AppSync | Application Load Balancer |
|---|---|---|---|
| プロトコル | REST API / HTTP API / WebSocket API | GraphQL（サブスクリプションによるリアルタイム配信）、AppSync Events（WebSocket の Pub/Sub） | HTTP / HTTPS、gRPC、WebSocket |
| 認証・認可 | IAM、Cognito、Lambda オーソライザー、JWT（HTTP API）、API キー | API キー、IAM、Cognito、OIDC、Lambda | OIDC / Cognito による認証アクション |
| 流量制御 | スロットリング、使用量プラン（API キーごとの上限） | WAF のレートベースルールなどで補う | WAF のレートベースルールなどで補う |
| キャッシュ | REST API のキャッシュ（HTTP API にはない） | サーバー側のキャッシュ | なし（前段に CloudFront を置く） |
| AWS WAF | REST API に関連付け可（HTTP API は不可） | 関連付け可 | 関連付け可 |
| 長い処理 | 統合のタイムアウトは既定 29 秒（リージョン / プライベートの REST API は引き上げ可、HTTP API は最大 30 秒） | 長い処理は非同期にする | アイドルタイムアウトを最大 4,000 秒まで設定可 |
| プライベートな API | プライベート REST API（インターフェイス VPC エンドポイント経由） | プライベート API | 内部向けの ALB |
| 料金の基準 | 要求数（WebSocket は接続時間とメッセージ数） | 操作の回数、リアルタイムの更新数、接続時間 | 時間と LCU |
| 向くケース | 外部公開 API、パートナー向けの API キーと使用量プラン、Lambda の前段 | モバイル・Web で複数のデータソースを 1 回の要求で取得、リアルタイムの更新 | コンテナへの大量の要求、長時間の要求、gRPC、要求単価を抑えたい |

- 世界中の利用者に配信するなら、どの入口の前にも CloudFront を置き、エッジでのキャッシュ、AWS WAF、AWS Shield を効かせます。
- API Gateway の 29 秒を超える処理は、要求を受け付けて 202 を返し、結果はポーリング、WebSocket、AppSync のサブスクリプションで返す **非同期の API** にするのが定石です。
- サービス間（東西方向）の通信には、入口のサービスではなく VPC Lattice や Service Connect を使います。

> [!TIP]
> **試験のポイント**: 「パートナーごとに API キーと呼び出し回数の上限」→ API Gateway の使用量プラン。「モバイルアプリで複数のマイクロサービスのデータをまとめて取得し、変更をリアルタイムに受け取る」→ AppSync。「最も低コストでシンプルな JWT 認証付きの API」→ HTTP API。「コンテナへの大量の HTTP 要求、gRPC」→ ALB。

> [!WARNING]
> **ひっかけ注意**: HTTP API には AWS WAF を直接関連付けられず、キャッシュ機能もありません。WAF が必要なら REST API を選ぶか、HTTP API の前段に CloudFront + WAF を置きます。

## 7. コンテナ戦略

### 7.1 ECS と EKS

| 観点 | Amazon ECS | Amazon EKS |
|---|---|---|
| API・エコシステム | AWS 独自のシンプルな API | Kubernetes の API とエコシステム（Helm、オペレーター、CNCF のツール） |
| コントロールプレーンの料金 | 追加料金なし | クラスターごとの時間料金（Kubernetes バージョンの延長サポート期間は割高） |
| バージョンアップ | 利用者の作業はほぼない | Kubernetes のバージョンアップを定期的に計画・実施する |
| 学習・運用の負荷 | 小さい | 大きい（EKS Auto Mode で軽減できる） |
| 移植性 | AWS に特化 | オンプレミスや他のクラウドと運用を共通化できる |
| サービス間通信 | ECS Service Connect、VPC Lattice | VPC Lattice、Kubernetes の Service、オープンソースのメッシュ |
| 向くケース | AWS に集中し、シンプルに運用したい | Kubernetes の資産とスキルがある、ハイブリッド / マルチクラウドで共通化したい |

### 7.2 実行基盤の選択肢

| 選択肢 | AWS が管理する範囲 | 特徴 |
|---|---|---|
| **ECS Express Mode** | Fargate のサービス、ALB、Auto Scaling、HTTPS の URL を一括で用意 | Web アプリや API を最短で公開できる。追加料金なし。App Runner（2026年4月30日に新規受付終了）の後継として推奨 |
| **Fargate**（ECS / EKS） | サーバー、OS、キャパシティ | タスク / Pod ごとに分離される。GPU や特権コンテナは使えない。Fargate Spot で割引 |
| **ECS Managed Instances** | ECS 用の EC2 のプロビジョニング、スケーリング、パッチ適用 | インスタンスタイプ（GPU を含む）を選びつつ、運用は AWS に任せる |
| ECS on EC2 | コントロールプレーンのみ | キャパシティプロバイダーで Auto Scaling グループを管理。最も柔軟 |
| **EKS Auto Mode** | ノードの自動プロビジョニング（Karpenter ベース）、ロードバランサーやストレージなどのコア機能、ノードの OS の更新 | Kubernetes の API を使いつつ、ノードの運用負荷を大きく減らせる |
| EKS + マネージドノードグループ / Karpenter | ノードのライフサイクルの一部 | ノードの構成を細かく制御できる |

```mermaid
flowchart TB
    Q0{"Kubernetes の API や<br/>エコシステムが必要か"}
    Q0 -- "はい" --> Q1{"ノードの運用を<br/>AWS に任せたいか"}
    Q1 -- "はい" --> K1["EKS Auto Mode"]
    Q1 -- "いいえ（細かく制御）" --> K2["EKS + マネージドノードグループ<br/>/ Karpenter"]
    Q0 -- "いいえ" --> Q2{"Web アプリや API を<br/>最短で公開したいか"}
    Q2 -- "はい" --> E1["ECS Express Mode"]
    Q2 -- "いいえ" --> Q3{"GPU や特定の<br/>インスタンスタイプが必要か"}
    Q3 -- "はい" --> E2["ECS Managed Instances<br/>（または ECS on EC2）"]
    Q3 -- "いいえ" --> E3["ECS on Fargate"]
```

### 7.3 マルチテナントのモデル

SaaS では、テナント（顧客）をどの単位で分離するかが、コスト・運用・セキュリティを左右します。

| モデル | 分離の単位 | 長所 | 短所 | 向くケース |
|---|---|---|---|---|
| サイロ | テナントごとのアカウント、クラスター、DB | 分離が最も強い。他のテナントの影響（ノイジーネイバー）がない。テナントごとのコストが明確 | コストと運用の手間が最も大きい | 規制の厳しい大口顧客、専用環境を求める上位プラン |
| プール | すべてのテナントでコンピューティングと DB を共有 | コスト効率と運用効率が最も高い | 分離をアプリと IAM で実装する必要がある。ノイジーネイバー | 多数の小規模なテナント |
| ブリッジ | 層ごとに使い分ける（例: Web 層は共有、DB はテナントごと） | 分離とコストの釣り合いを取れる | 設計が複雑になる | 多くの SaaS |

プールで分離を守る代表的な方法は次のとおりです。

- **テナントのコンテキストを伝える**: 認証済みのトークン（JWT）にテナント ID を入れ、すべての処理がそれを使います。
- **IAM で分離を強制する**: テナント ID を含むセッションポリシーで一時的な認証情報を発行し、DynamoDB では `dynamodb:LeadingKeys` 条件でパーティションキーがテナント ID の項目だけに制限します。EKS Pod Identity のセッションタグ（名前空間やサービスアカウント）を使った属性ベースのアクセス制御（ABAC）も有効です。
- **EKS では名前空間ごとに分ける**: ネットワークポリシーで通信を制限し、リソースクォータでノイジーネイバーを抑えます。上位プランのテナントには専用のノードやクラスターを割り当てます（階層ごとのブリッジ）。
- **コストを按分する**: ECS / EKS の分割コスト配分データで、共有クラスターのコストをタスクや Pod の単位で配分します。

> [!TIP]
> **試験のポイント**: 「Kubernetes の運用負荷を最小に」→ EKS Auto Mode。「コンテナの Web アプリを最小の手間で公開（App Runner の代わり）」→ ECS Express Mode。「GPU を使うコンテナを、インスタンスの運用なしで」→ ECS Managed Instances。「テナントごとに厳格な分離とコストの明確化」→ サイロ。「多数の小規模テナントでコスト効率」→ プール。

## 8. コンテナセキュリティ

コンテナのセキュリティは、ビルドから実行までの各段階に対策を重ねる「多層防御」で考えます。

```mermaid
flowchart LR
    CODE["コード"] --> BUILD["ビルド<br/>（CodeBuild など）"]
    BUILD --> SCAN["脆弱性スキャン<br/>（Amazon Inspector）"]
    SCAN -- "合格" --> SIGN["署名<br/>（AWS Signer + Notation）"]
    SIGN --> ECR["Amazon ECR<br/>（継続的スキャン）"]
    ECR --> VERIFY["署名の検証<br/>（EKS のアドミッション制御）"]
    VERIFY --> RUN["実行<br/>（最小権限・シークレット注入・<br/>読み取り専用のルート FS）"]
    RUN --> MON["ランタイムの監視<br/>（GuardDuty Runtime Monitoring）"]
```

| 層 | 主なリスク | 対策 | AWS の主な手段 |
|---|---|---|---|
| ビルド | 脆弱なライブラリ、秘密情報の埋め込み | 最小のベースイメージ、依存関係のスキャン、秘密情報をイメージに入れない | Amazon Inspector（コードセキュリティ、CI/CD 連携）、CodeBuild |
| レジストリ | 改ざん、脆弱なイメージの放置 | タグの不変性、継続的なスキャン、署名 | Amazon ECR（タグのイミュータビリティ、拡張スキャン）、AWS Signer |
| デプロイ | 承認されていないイメージの実行 | 署名の検証、ダイジェストによるイメージの指定 | EKS のアドミッション制御（Kyverno、Ratify + OPA Gatekeeper） |
| 実行 | 権限の悪用、コンテナからの脱出 | 最小権限のロール、読み取り専用のルートファイルシステム、非 root、特権の禁止 | タスクロール、EKS Pod Identity、Fargate |
| ネットワーク | 横方向の移動 | タスク / Pod ごとのセキュリティグループ、ネットワークポリシー | awsvpc モード、Pod のセキュリティグループ、VPC CNI のネットワークポリシー |
| 検知と対応 | 侵害の見逃し | ランタイムの脅威検出、監査ログ、自動対応 | GuardDuty Runtime Monitoring、EKS の監査ログ、EventBridge |

### 8.1 イメージのスキャン

| 観点 | ECR の基本スキャン | ECR の拡張スキャン（Amazon Inspector） |
|---|---|---|
| 対象 | OS のパッケージ | OS のパッケージとプログラミング言語のパッケージ |
| タイミング | プッシュ時、または手動 | プッシュ時に加えて、新しい脆弱性（CVE）が公開されるたびに継続的に再評価 |
| 結果の扱い | ECR のコンソール・API | Inspector に集約し、EventBridge で自動対応。統合された AWS Security Hub にも連携 |

- パイプラインでは、ECR へプッシュする前に Inspector の CI/CD 連携でイメージをスキャンし、重大な脆弱性があればビルドを失敗させます。ソースコードの段階では、Inspector のコードセキュリティ（SAST、SCA、IaC のスキャン）も使えます。
- 組織全体では、AWS Organizations の Inspector ポリシーで全アカウントのスキャンを有効にし、検出結果は委任管理者のアカウントに集約します。

### 8.2 イメージの署名と検証

スキャンに合格したイメージだけを実行するには、**署名** で「誰がビルドし、改ざんされていないか」を保証します。

- パイプラインでスキャンに合格したイメージに、**AWS Signer** と **Notation**（CNCF の Notary Project）の CLI で署名します。署名はイメージと関連付けて ECR に保存されます。
- **EKS** では、アドミッションコントローラー（Kyverno、または Ratify + OPA Gatekeeper と AWS Signer のプラグイン）で、信頼する署名プロファイルの署名がないイメージの起動を拒否します。
- **ECS** には、起動時に署名を検証する仕組みが組み込まれていません。パイプラインで署名を検証してからデプロイし、タスク定義ではイメージをタグではなく **ダイジェスト**（`@sha256:...`）で指定します。タスク定義やサービスを更新できる IAM の権限も、パイプラインのロールに限定します。
- 侵害された署名プロファイルは、AWS Signer で失効させられます。

### 8.3 最小権限の IAM

| 対象 | ロール | 使いどころ |
|---|---|---|
| ECS | **タスク実行ロール** | ECS のエージェントが使う。ECR からのイメージの取得、CloudWatch Logs への書き込み、注入するシークレットの取得 |
| ECS | **タスクロール** | アプリのコードが AWS の API を呼ぶときに使う。サービスごとに分け、必要なリソースと操作だけを許可する |
| EKS | **EKS Pod Identity**（推奨）/ IRSA | サービスアカウント単位で IAM ロールを割り当てる。Pod Identity は OIDC プロバイダーが不要で、セッションタグを使った ABAC もできる |

- EC2 ノードの IAM ロールに、アプリ用の権限を付けてはいけません。Pod やタスクからインスタンスメタデータ（IMDS）経由でノードのロールを使えないよう、IMDSv2 のホップ数の上限を 1 にするなどしてアクセスを遮断します。
- 1 つのロールを複数のサービスで使い回さないことで、侵害されたときの影響範囲を限定します。

### 8.4 シークレットの注入

- **ECS**: タスク定義の `secrets` で、`valueFrom` に Secrets Manager のシークレットや Parameter Store のパラメーターの ARN を指定すると、コンテナの起動時に環境変数として注入されます。取得の権限はタスク実行ロールに付けます。注入された値は起動時点のものなので、**ローテーション後の値は新しいタスクで反映** されます（サービスを再デプロイするか、アプリが実行時にキャッシュ付きで取得する）。
- **EKS**: Secrets Store CSI Driver と AWS Secrets and Configuration Provider（ASCP）で、Secrets Manager の値をファイルとして Pod にマウントします。Kubernetes の Secret を使う場合は、KMS によるエンベロープ暗号化で保護します。
- **禁止事項**: イメージや Git リポジトリへの埋め込み、タスク定義やマニフェストへの平文での記載。

### 8.5 ランタイムの強化と監視

- **読み取り専用のルートファイルシステム**: ECS の `readonlyRootFilesystem`、Kubernetes の `readOnlyRootFilesystem` を有効にし、書き込みが必要な場所（一時ファイルなど）だけボリュームをマウントします。攻撃者がツールを置いたり、実行ファイルを書き換えたりするのを防げます。
- **非 root ユーザーで実行し、不要な Linux ケーパビリティを外します**。特権コンテナは使いません（Fargate では特権コンテナを使えず、追加できるケーパビリティも SYS_PTRACE のみです）。
- **GuardDuty Runtime Monitoring**: EKS、ECS（Fargate / EC2）、EC2 で、プロセスの実行、ファイルへのアクセス、ネットワーク接続などの OS レベルのイベントを監視し、暗号通貨のマイニング、リバースシェル、権限昇格などの疑わしい動きを検出します。セキュリティエージェントは GuardDuty が自動で管理できます（EKS ではアドオン、ECS on Fargate ではタスクに自動で追加）。検出結果は EventBridge 経由で、タスクの停止や隔離などの自動対応につなげます。
- 検出結果は、統合された AWS Security Hub（2025年12月に一般提供開始）で、Inspector の脆弱性などと関連付けて優先順位を判断できます。

> [!TIP]
> **試験のポイント**: 「新しい CVE が公開されたら既存のイメージも再評価」→ ECR の拡張スキャン（Inspector）。「署名されたイメージだけを EKS で実行」→ AWS Signer + Notation とアドミッション制御。「コンテナ内での暗号通貨のマイニングを検出」→ GuardDuty Runtime Monitoring。「Pod ごとに異なる AWS の権限」→ EKS Pod Identity（または IRSA）。「コンテナにシークレットを安全に渡す」→ ECS の `secrets` / Secrets Store CSI Driver。

> [!WARNING]
> **ひっかけ注意**: タスク実行ロールとタスクロールを取り違えないでください。アプリが S3 や DynamoDB を呼ぶ権限は **タスクロール** に付けます。また、VPC フローログは通信の記録であり、コンテナ内のプロセスの挙動（マイニングなど）は検出できません。

## 9. データ管理パターン

### 9.1 Database per service

マイクロサービスでは、**各サービスが自分のデータを所有し、他のサービスの DB に直接アクセスさせない** のが原則です。

- **理由**: スキーマの変更、スケーリング、障害の影響を、サービスごとに独立させるためです。アクセスのパターンに合った DB（DynamoDB、Aurora、OpenSearch など）をサービスごとに選べます（ポリグロットパーシステンス）。
- **実装**: DB のクラスターを分けるのが最も明確ですが、少なくともスキーマと認証情報を分けます。他のサービスのデータは、API かイベントで受け取ります。
- **代償**: サービスをまたぐ結合ができないため、API の合成（複数の API の結果をまとめる）や CQRS の読み取りモデルで補います。サービスをまたぐ更新の整合性は Saga（4.4 節）で扱います。

移行期間中にモノリスの DB を一時的に共有することはありますが、最終的には分離します（[移行とモダナイゼーション](07-migration-modernization.md) のストラングラーフィグを参照）。

### 9.2 CQRS

**CQRS（コマンドクエリ責務分離）** は、書き込みのモデルと読み取りのモデルを分け、それぞれに最適なデータストアを使うパターンです。

- 書き込みは DynamoDB や Aurora に行い、その変更（DynamoDB Streams、CDC、イベント）を使って、検索用の OpenSearch Service、集計済みのビューを持つ DynamoDB のテーブル、ランキング用の ElastiCache、分析用の Redshift などの読み取りモデルを更新します。
- 読み取りモデルは **結果整合性** になります。書き込み直後の画面には、書き込みの応答の内容を表示するなど、利用者の体験を設計で補います。
- 読み取りモデルが壊れても、変更の履歴から作り直せるようにしておきます。

### 9.3 イベントソーシング

**イベントソーシング** は、現在の状態ではなく、状態を変えた **イベントの列** を追記専用で保存し、現在の状態はイベントを再生して求めるパターンです。変更の完全な履歴（監査証跡）が残り、任意の時点の状態を再現できます。

- **イベントストア**: DynamoDB で、パーティションキーを集約の ID、ソートキーをバージョン番号にし、条件付き書き込み（同じバージョンが存在しないこと）で楽観的な同時実行制御を行う形が代表的です。DynamoDB Streams で読み取りモデル（投影）を更新します。
- **スナップショット**: イベントが増えると再生に時間がかかるため、一定間隔で状態のスナップショットを保存します。
- **注意点**: 設計と運用が複雑になり、イベントのスキーマの進化も難しくなります。監査や時点の再現が本当に必要な領域に限って使います。

> [!NOTE]
> 古い教材では、改ざんできない台帳として **Amazon QLDB** が登場します。QLDB は 2025年7月31日にサービスを終了しました。新しい設計では、DynamoDB や Aurora PostgreSQL へのイベントの追記と、S3 オブジェクトロックによる改ざん防止の保管などを組み合わせます。

### 9.4 トランザクションアウトボックス

「DB を更新してから EventBridge にイベントを発行する」処理は、2 つの書き込みを原子的に行えません（二重書き込みの問題）。DB の更新後に異常終了すればイベントが失われ、発行後に DB の更新が失敗すれば存在しない注文のイベントが流れます。

**トランザクションアウトボックス** パターンでは、業務データと「送るべきイベント（アウトボックス）」を **同じローカルトランザクション** で書き込み、別の仕組みがアウトボックスを読んで発行します。

```mermaid
flowchart LR
    APP["注文サービス"] -- "1 つのトランザクションで<br/>注文とアウトボックスを書く" --> DDB[("DynamoDB<br/>（TransactWriteItems）")]
    DDB -- "DynamoDB Streams" --> PIPE["EventBridge Pipes<br/>（アウトボックスの項目だけを<br/>フィルター・整形）"]
    PIPE --> BUS["EventBridge<br/>イベントバス"]
    BUS --> C1["在庫サービス"]
    BUS --> C2["通知サービス"]
```

- **DynamoDB の場合**: `TransactWriteItems` で注文の項目とアウトボックスの項目を書き、DynamoDB Streams → EventBridge Pipes → EventBridge で発行します。つなぎのコードは不要です。
- **Aurora / RDS の場合**: 業務テーブルと同じトランザクションでアウトボックスのテーブルに書き、CDC（DMS、または Amazon MSK Connect 上の Debezium）で Kinesis や MSK に流します。
- 発行は少なくとも 1 回になるため、受け取り側は冪等にします（4.6 節）。

### 9.5 キャッシュ戦略

| 層 | 手段 | キャッシュする対象 | 注意点 |
|---|---|---|---|
| エッジ | CloudFront | 静的コンテンツ、API の応答 | キャッシュキーの設計、無効化、個人のデータをキャッシュしない |
| API | API Gateway（REST API）のキャッシュ、AppSync のキャッシュ | API の応答 | HTTP API にはキャッシュ機能がない |
| アプリと DB の間 | Amazon ElastiCache（Valkey / Redis OSS / Memcached、サーバーレスもあり） | クエリの結果、セッション、ランキング | 遅延読み込み（キャッシュアサイド）かライトスルーか、TTL の設計 |
| DynamoDB の前 | DynamoDB Accelerator（DAX） | 項目とクエリの結果（マイクロ秒の読み取り） | キャッシュされるのは結果整合性の読み込みだけ。強い整合性の読み込みは DynamoDB へそのまま渡る |
| 読み取りの分散 | Aurora レプリカ、リードレプリカ | ― | キャッシュではない。レプリカの遅延に注意 |
| 実行環境の中 | Lambda の実行環境の再利用、アプリのメモリ | 設定値、DB 接続 | インスタンスごとに値が異なる |

- **キャッシュの一斉失効（スタンピード）**: 人気のキーが同時に失効すると、DB に要求が殺到します。TTL にばらつき（ジッター）を持たせる、再計算を 1 つの要求に絞る、CloudFront の Origin Shield で要求をまとめる、などで防ぎます。
- **無効化のタイミング**: データの変更イベント（9.4 節）をきっかけにキャッシュを削除・更新すると、TTL だけに頼るより新しさを保てます。

## 10. 既存システムの継続的改善

SAP-C02 の第3分野「既存のソリューションの継続的な改善」で問われてきた改善の型は、SAP-C03 でも重要です。問題文の「兆候」から、改善のパターンを選べるようにしておきます。

| 課題 | 兆候 | 改善のパターン | AWS の主な手段 |
|---|---|---|---|
| 読み取りの性能 | DB の CPU 使用率が高い、同じクエリの繰り返し | キャッシュ、リードレプリカ、CQRS | ElastiCache、DAX、Aurora レプリカ |
| 書き込みの急増 | ピーク時の書き込みの失敗、スロットリング | キューによる平準化、書き込みのバッチ化 | SQS、Kinesis、DynamoDB オンデマンド |
| 障害の連鎖 | 1 つのサービスの遅延で全体がタイムアウト | 非同期化、タイムアウト、サーキットブレーカー、バルクヘッド | EventBridge、SQS、Step Functions |
| 単一障害点 | 1 つの AZ やインスタンスの障害で停止 | マルチ AZ、静的安定性 | Auto Scaling、マルチ AZ 配置 |
| デプロイの失敗 | リリース後の障害が多い | ブルー/グリーン、カナリア、自動ロールバック | ECS の組み込みブルー/グリーン、Lambda のエイリアスの加重、CodeDeploy |
| 原因調査の遅さ | 障害の復旧に時間がかかる | 構造化ログ、分散トレース、SLO、AI による調査支援 | CloudWatch Application Signals、X-Ray、CloudWatch investigations |
| 低い使用率 | 常時稼働のサーバーの使用率が低い | サーバーレス化、ライトサイジング、Graviton、Savings Plans | Lambda、Fargate、Compute Optimizer |
| バッチの長期化 | 夜間バッチが時間内に終わらない | 並列化、イベント駆動化 | Step Functions の Distributed Map |

改善は「SLO で測る → ボトルネックを特定する → 仮説を立てる → 安全なデプロイで小さく変える → 効果を確認する」の繰り返しで進めます。運用の自動化と可観測性は [運用上の優秀性と自動化](12-operational-excellence.md)、回復性の検証は [回復力と事業継続](06-resilience-business-continuity.md) で扱います。

## 典型シナリオと解法

### シナリオ 1: セール時に注文処理が連鎖的に失敗する

- **状況**: 注文 API が、決済・在庫・ポイント・通知の 4 つのサービスを同期で順に呼んでいる。セール時に通知サービスが遅延し、注文 API 全体がタイムアウトした。クライアントの再送で二重の請求も発生した。
- **要件**: 注文の受け付けを止めない。決済と在庫の整合性を保つ。二重の請求を防ぐ。
- **推奨設計**: 注文 API は注文を DynamoDB に保存し、アウトボックス（DynamoDB Streams → EventBridge Pipes）で OrderPlaced を EventBridge に発行する。決済と在庫は Step Functions の Standard ワークフローで Saga として実行し（補償は返金と引き当ての解除）、決済の API には注文 ID を冪等性キーとして渡す。ポイントと通知は EventBridge のルール → SQS で非同期に処理し、DLQ を設定する。
- **他の選択肢が適さない理由**: インスタンスを大きくしても同期の連鎖は解消しない。すべてを 1 つのワークフローに入れると、独立してよい通知やポイントまで結合する。リトライの回数を増やすだけでは、二重の請求が悪化する。

### シナリオ 2: App Mesh からの移行

- **状況**: アカウント A の ECS のサービス群は App Mesh で通信している。アカウント B の EKS のサービスが、アカウント A の API を呼んでいる。一部の VPC の CIDR は重複している。
- **要件**: App Mesh のサポート終了（2026年9月30日）までに移行する。サイドカーの運用をやめる。アカウント間の呼び出しは IAM で認可する。
- **推奨設計**: アカウント A の ECS のサービス同士は **ECS Service Connect** に移す。アカウントをまたぐ通信と EKS からの呼び出しには **VPC Lattice** のサービスネットワークを使い、RAM で共有して認証ポリシーで認可する。EKS は AWS Gateway API Controller で統合する。
- **他の選択肢が適さない理由**: App Mesh の継続はサポート終了で不可。VPC ピアリングは CIDR が重複していると使えない。Transit Gateway と内部 NLB の組み合わせは IAM による認可がなく、サービスごとの設定が増える。自社運用の Istio は運用負荷が大きく、ECS では使いにくい。

### シナリオ 3: 取引先ファイルのサーバーレスパイプライン

- **状況**: 200 社の取引先が不定期に CSV ファイルを S3 にアップロードする。現在は EC2 の cron で 1 時間ごとに処理しており、不正なファイルが 1 つあると処理全体が止まる。
- **要件**: 到着後すぐに処理する。不正なファイルは隔離して他の処理を続ける。サーバーの管理をなくす。分析用に列指向の形式で保存する。
- **推奨設計**: S3 のイベント → EventBridge → Step Functions の Standard ワークフロー（検証 → Glue ジョブ（.sync で完了を待つ）で Parquet / Iceberg に変換 → Glue Data Catalog の更新）。検証や変換に失敗したファイルは Catch で隔離用のプレフィックスへ移し、担当者に通知する。
- **他の選択肢が適さない理由**: AWS Data Pipeline は新規受付終了。EC2 の cron は運用負荷と遅延が大きい。1 つの Lambda 関数ですべてを処理すると、15 分の制限とエラー処理の複雑さが問題になる。

### シナリオ 4: AI を使った文書処理を開発チームがコードで管理する

- **状況**: アプリの開発チームが、契約書の PDF をアップロードすると、テキストの抽出 → Amazon Bedrock による要約とリスク判定 → 担当者の確認（最大 3 日）→ 結果の登録、と進む処理を作る。チームは Python に習熟しており、処理をコードで書き、ユニットテストもコードで書きたい。
- **要件**: 途中の障害から続きで再開できる。担当者の確認を待つ間は料金を抑える。
- **推奨設計**: **Lambda durable functions** で、各処理をステップとして書き、担当者の確認はコールバックで待つ（待機中はコンピューティングの料金がかからない）。乱数や現在時刻などはステップの中で扱い、リプレイで結果が変わらないようにする。運用担当者にも流れを可視化したい、多数の AWS サービスをコードなしでつなぎたい場合は、Step Functions の Standard ワークフロー + タスクトークンも要件を満たす。
- **他の選択肢が適さない理由**: 1 回の Lambda の呼び出しで待つと 15 分の上限を超える。SQS の遅延キューは最大 15 分。Express ワークフローは 5 分までで、コールバックにも対応していない。

### シナリオ 5: マルチテナント SaaS のテナント分離

- **状況**: テナントは 2,000 社で、大半は小規模。上位プランの 20 社は、契約で専用の環境とデータの分離を求めている。Kubernetes を使っているが、ノードの運用負荷が大きい。
- **要件**: 契約の分離要件を満たしつつ、全体のコストと運用負荷を抑える。テナントごとのコストを把握する。
- **推奨設計**: 階層ごとのブリッジモデル。標準プランはプール（共有の EKS Auto Mode のクラスター、名前空間ごとのネットワークポリシーとリソースクォータ、テナント ID を使った IAM の条件でデータを分離）。上位プランはサイロ（テナントごとのアカウントに専用のクラスターと DB）。分割コスト配分データで、共有部分のコストをテナントに按分する。
- **他の選択肢が適さない理由**: 全テナントをサイロにすると、2,000 の環境の運用とコストが過大になる。全テナントをプールにすると、上位プランの契約要件を満たせない。

### シナリオ 6: 規制業界のコンテナセキュリティ

- **状況**: 金融系の企業が EKS で決済 API を運用している。監査で、「実行中のコンテナが承認済みのイメージであることの証明」「既知の脆弱性の継続的な把握」「実行時の不審な挙動の検出」「認証情報をイメージに含めないこと」を求められた。
- **推奨設計**: Inspector の CI/CD 連携と ECR の拡張スキャンで脆弱性を継続的に評価し、合格したイメージに AWS Signer + Notation で署名、Kyverno（または Ratify + Gatekeeper）でアドミッション時に検証する。EKS Pod Identity で Pod ごとに最小権限のロールを割り当て、シークレットは Secrets Store CSI Driver + ASCP で渡す。読み取り専用のルートファイルシステムと非 root で実行し、GuardDuty Runtime Monitoring の検出結果を EventBridge で受けて自動で隔離する。
- **他の選択肢が適さない理由**: 基本スキャンだけでは言語のパッケージと継続的な再評価をカバーできない。ノードのロールに権限を付けると、すべての Pod が同じ権限を持つ。マニフェストの環境変数に平文で書くと、認証情報が漏れる。VPC フローログではプロセスの挙動を検出できない。

### シナリオ 7: 検索が重い商品カタログ

- **状況**: 商品カタログを Aurora MySQL で管理している。LIKE を使った全文検索と絞り込みのクエリで、DB の CPU 使用率が 90% に達している。更新は 1 日数千件、閲覧は毎秒数万件。
- **要件**: 検索の応答時間を短くし、DB の負荷を下げる。更新は数秒以内に検索結果へ反映されればよい。
- **推奨設計**: CQRS。書き込みは Aurora のまま、変更を CDC（DMS は OpenSearch Service をターゲットにできる）で Amazon OpenSearch Service に反映し、検索はそちらで行う。商品の詳細ページは CloudFront と ElastiCache でキャッシュし、更新のイベントで無効化する。
- **他の選択肢が適さない理由**: Aurora レプリカを増やしても、LIKE による検索の非効率は解消しない。インスタンスを大きくするのはコストが高く、いずれ上限に達する。DAX は DynamoDB 専用で、Aurora には使えない。

## まとめ

- クラウドネイティブとは、弾力性・マネージドサービス・従量課金・自動化を前提に設計することです。マイクロサービスは手段であり、分散のコスト（ネットワーク障害、結果整合性、調査の難しさ）と引き換えであることを理解して選びます。
- イベント駆動の中心は **EventBridge** です。少なくとも 1 回の配信・順序の保証なし・再試行は最大 24 時間 / 185 回・最大イベントサイズ 1 MB（古い教材では 256 KB）を前提に、受け取り側を冪等にし、DLQ とアーカイブで再処理に備えます。
- ドメインの中は **オーケストレーション**（Step Functions）、ドメインの間は **コレオグラフィ**（EventBridge）で結ぶのが定石です。
- サーバーレスのデータパイプラインは、S3 のイベント → EventBridge → Step Functions、Kinesis → Lambda / Firehose を基本形に、冪等な書き込み・失敗の隔離・背圧の制御を設計します。Data Pipeline は新規受付終了です。
- Step Functions は、長時間・承認・監査なら **Standard**（1 年、正確に 1 回、タスクトークン、redrive）、大量で短い処理なら **Express**（5 分）です。大量の並列処理は **Distributed Map**（最大 10,000 の子ワークフロー）を使います。
- サービスをまたぐ整合性は **Saga**（逆順・冪等・再試行可能な補償）で扱い、重複は **冪等性キー** で吸収します。**Lambda durable functions** は、コードのまま最大 1 年の多段処理を書ける新しい選択肢です。
- **App Mesh は 2026年9月30日にサポート終了** です。ECS 同士は **ECS Service Connect**、EKS・Lambda・アカウントや VPC をまたぐ通信は **VPC Lattice**（認証ポリシー、CIDR の重複可）へ移行します。
- 入口は、API キーと使用量プランなら API Gateway、GraphQL とリアルタイム更新なら AppSync、コンテナへの大量の要求や gRPC なら ALB を選びます。
- コンテナの実行基盤は、最短の公開なら ECS Express Mode、サーバーレスなら Fargate、GPU なら ECS Managed Instances、Kubernetes の運用負荷を減らすなら EKS Auto Mode です。マルチテナントはサイロ / プール / ブリッジで分離とコストの釣り合いを取ります。
- コンテナセキュリティは、Inspector による継続的なスキャン、AWS Signer + Notation の署名とアドミッション制御、タスクロール / Pod Identity の最小権限、シークレットの注入、読み取り専用のルート FS、GuardDuty Runtime Monitoring を重ねます。データは Database per service を原則に、CQRS、イベントソーシング、トランザクションアウトボックス、多層のキャッシュを使い分けます。

## 確認問題

### 問1

ある金融機関は、融資の申し込みを処理するワークフローを構築しています。自動審査の後、担当者が内容を確認して承認または却下します。担当者の確認には最大 10 日かかることがあり、10 日を過ぎたら上長へエスカレーションする必要があります。監査のため、各手順の入力と出力の履歴を後から確認できる必要があります。運用上のオーバーヘッドが最も少ない設計はどれですか。

- A. Step Functions の Standard ワークフローで、承認のステップを .waitForTaskToken の統合パターンにし、タスクトークンを含む承認依頼を送る。承認用の API から SendTaskSuccess または SendTaskFailure を呼び出す。ステップの TimeoutSeconds を 10 日に設定し、States.Timeout を Catch してエスカレーションのステートへ進める。
- B. Step Functions の Express ワークフローで Wait ステートを 10 日に設定し、待機後に DynamoDB で承認結果を確認する。
- C. SQS の遅延キューで 10 日後にメッセージを配信し、Lambda 関数が承認状況を確認してエスカレーションする。
- D. Lambda 関数の中で承認されるまでポーリングを繰り返し、10 日経過したらエスカレーションする。

<details>
<summary>解答と解説</summary>

**正解: A**

**解説**: 人の承認を待つには、Standard ワークフローのコールバック（.waitForTaskToken）の統合パターンを使います。実行は最大 1 年まで一時停止でき、待機中はコンピューティングが動きません。TimeoutSeconds を超えると States.Timeout になるため、Catch でエスカレーションに分岐できます。Standard ワークフローは各ステートの入力と出力を実行履歴として残すため、監査の要件も満たします。

**各選択肢の検討**
- A: ✓ 待機、タイムアウト時の分岐、監査の履歴を、コードをほとんど書かずに実現できます。
- B: ✗ Express ワークフローの実行は最長 5 分で、10 日は待てません。コールバックにも対応していません。
- C: ✗ SQS の遅延キューの遅延は最大 15 分です。状態の管理と監査の履歴も自作が必要です。
- D: ✗ Lambda の 1 回の実行は最大 15 分です。ポーリングは無駄なコストもかかります。

</details>

### 問2

ある企業は 2 つの AWS アカウントでマイクロサービスを運用しています。アカウント A では Amazon ECS のサービス群が AWS App Mesh で通信し、アカウント B の Amazon EKS のサービスがアカウント A の API を呼び出しています。2 つのアカウントの VPC は CIDR が重複しています。App Mesh のサポート終了に備え、サイドカーのプロキシを自社で運用せずに、アカウントをまたぐ呼び出しを IAM で認可できる構成へ移行する必要があります。最も適切な方法はどれですか。

- A. App Mesh を使い続け、Envoy のサイドカーのイメージを最新に更新する。
- B. すべてのサービスを ECS Service Connect の同じ名前空間に登録し、アカウント B の EKS からも Service Connect の短い名前で呼び出す。
- C. Amazon VPC Lattice のサービスネットワークを作成して AWS RAM でアカウント B と共有し、アカウント A の ECS のサービスを VPC Lattice のサービスとして登録する。EKS 側は AWS Gateway API Controller で統合し、サービスネットワークとサービスの認証ポリシーで呼び出し元の IAM ロールを認可する。
- D. 2 つの VPC を VPC ピアリングで接続し、アカウント A のサービスの前に内部向けの NLB を置いて、Cloud Map の DNS 名で呼び出す。

<details>
<summary>解答と解説</summary>

**正解: C**

**解説**: VPC Lattice は、サイドカーなしで ECS・EKS・Lambda などをまたいでサービス間の通信を提供し、サービスネットワークを RAM でアカウント間に共有できます。VPC の CIDR が重複していても使え、認証ポリシーで SigV4 の要求を IAM で認可できます。App Mesh の移行先として、アカウントや VPC、コンピューティングの種類をまたぐ場合の第一候補です。

**各選択肢の検討**
- A: ✗ App Mesh は 2026年9月30日にサポートが終了するため、使い続けられません。
- B: ✗ ECS Service Connect は ECS のサービス同士の通信のための機能で、EKS のサービスを名前空間に参加させることはできません。
- C: ✓ サイドカーの運用なし、アカウント間の接続、IAM による認可、CIDR の重複のすべてに対応します。
- D: ✗ CIDR が重複した VPC はピアリングで接続できません。IAM による認可もありません。

</details>

### 問3

あるメディア企業は、S3 バケットに保存された 3,000 万個の画像ファイルについて、メタデータを抽出して DynamoDB に登録するバッチ処理を毎月実行します。1 ファイルの処理は Lambda 関数で数秒で終わります。処理は 4 時間以内に完了する必要があり、DynamoDB の書き込み容量を超えないように並列度を制御したいと考えています。0.1% までのファイルの失敗は許容し、失敗したファイルを後から特定して再処理できるようにする必要があります。運用上のオーバーヘッドが最も少ない方法はどれですか。

- A. 1 つの Lambda 関数で S3 のオブジェクトの一覧を取得し、ループで順に処理する。
- B. Step Functions の Standard ワークフローでインライン Map を使い、すべてのファイルを並列に処理する。
- C. EC2 の Auto Scaling グループでワーカーを起動し、cron で処理のスクリプトを実行する。
- D. Step Functions の Distributed Map で S3 インベントリから処理対象を読み込み、要素をバッチ化して Express の子ワークフローで Lambda 関数を呼び出す。MaxConcurrency で並列度を制御し、ToleratedFailurePercentage を 0.1 に設定し、ResultWriter で結果を S3 に書き出す。

<details>
<summary>解答と解説</summary>

**正解: D**

**解説**: Distributed Map は、S3 の大量のオブジェクトを最大 10,000 の子ワークフローで並列に処理でき、並列度の上限、許容する失敗の割合、結果の書き出しを設定で指定できます。短い処理の子ワークフローを Express にし、要素をバッチ化すると、起動の回数とコストを抑えられます。書き出した結果から失敗したファイルを特定して再処理できます。

**各選択肢の検討**
- A: ✗ Lambda の 1 回の実行は最大 15 分で、3,000 万ファイルを順に処理できません。
- B: ✗ インライン Map の同時実行は最大 40 で、すべてが 1 つの実行履歴（25,000 イベントの上限）に記録されるため、この規模には使えません。
- C: ✗ サーバーの管理、スケーリング、失敗の追跡を自作する必要があり、運用負荷が大きくなります。
- D: ✓ 期限、並列度の制御、失敗の許容と再処理のすべてを、設定だけで満たします。

</details>

### 問4

ある企業の注文サービスは、注文を Amazon DynamoDB に書き込んだ後、アプリケーションのコードから Amazon EventBridge に OrderPlaced イベントを発行しています。まれにアプリケーションが書き込みの直後に異常終了し、注文は保存されているのにイベントが発行されない事象が起きています。注文が保存された場合には必ずイベントが発行されるようにする必要があります。受け取り側は重複したイベントを処理できます。運用上のオーバーヘッドが最も少ない設計はどれですか。

- A. 先にイベントを発行してから、注文を DynamoDB に書き込むように処理の順序を変える。
- B. TransactWriteItems で注文の項目とアウトボックスの項目を 1 つのトランザクションで書き込む。DynamoDB Streams を EventBridge Pipes のソースにしてアウトボックスの項目だけをフィルターし、EventBridge のイベントバスへ送る。
- C. DynamoDB と EventBridge への書き込みを 2 フェーズコミットでまとめる分散トランザクションを実装する。
- D. PutEvents が失敗したときに 3 回再試行し、それでも失敗した場合はエラーをログに出力する。

<details>
<summary>解答と解説</summary>

**正解: B**

**解説**: DB の更新とイベントの発行を原子的に行えない「二重書き込み」の問題には、トランザクションアウトボックスのパターンを使います。注文とアウトボックスを同じトランザクションで書けば、注文が保存されたときだけアウトボックスも残ります。DynamoDB Streams と EventBridge Pipes で発行すれば、つなぎのコードも不要です。発行は少なくとも 1 回になりますが、受け取り側は重複を処理できるため問題ありません。

**各選択肢の検討**
- A: ✗ 書き込みが失敗すると、存在しない注文のイベントが発行されます。問題が逆向きになるだけです。
- B: ✓ 注文の保存とイベントの発行の整合性を、マネージドなサービスの組み合わせで保証します。
- C: ✗ EventBridge は 2 フェーズコミットに参加できません。実装できたとしても複雑で、運用負荷が大きくなります。
- D: ✗ 書き込みの直後にアプリケーションが異常終了した場合は、再試行のコード自体が実行されません。

</details>

### 問5

ある企業は Amazon EKS で決済 API を運用しています。セキュリティ部門から次の要件が出されました。

- CI/CD パイプラインで脆弱性スキャンに合格し、署名されたイメージだけを本番のクラスターで実行する
- 実行中のコンテナでの暗号通貨のマイニングやリバースシェルなどの不審な挙動を検出する

これらの要件を満たす対策はどれですか。2 つ選択してください。

- A. ECR の基本スキャンをプッシュ時に有効にし、スキャン済みのイメージには "scanned-" で始まるタグを付けてデプロイする。
- B. VPC フローログを有効にし、Amazon Athena で週に 1 回分析する。
- C. パイプラインで Amazon Inspector のスキャンに合格したイメージに AWS Signer と Notation で署名し、Kyverno（または Ratify と OPA Gatekeeper）のアドミッション制御で、信頼する署名のないイメージの起動を拒否する。
- D. すべての Pod に同じ IAM ロールを割り当て、ノードの IAM ロールにも同じ権限を付けて設定を単純にする。
- E. EKS で GuardDuty Runtime Monitoring を有効にしてセキュリティエージェントの管理を自動化し、検出結果を EventBridge で受けて対応を自動化する。

<details>
<summary>解答と解説</summary>

**正解: C, E**

**解説**: 「スキャンに合格し、署名されたイメージだけを実行する」には、パイプラインでの署名と、クラスター側での署名の検証（アドミッション制御）の組み合わせが必要です。「実行中のコンテナの不審な挙動」は、OS レベルのイベントを監視する GuardDuty Runtime Monitoring で検出します。

**各選択肢の検討**
- A: ✗ タグの名前は誰でも付けられるため、統制になりません。基本スキャンは言語のパッケージや継続的な再評価にも対応していません。
- B: ✗ VPC フローログは通信の記録で、コンテナ内のプロセスの挙動は検出できません。週 1 回の分析では検出も遅れます。
- C: ✓ 署名で改ざんがなく承認済みであることを保証し、アドミッション制御で未署名のイメージの実行を防ぎます。
- D: ✗ 最小権限に反し、要件のどちらにも役立ちません。
- E: ✓ マイニングやリバースシェルなどのランタイムの脅威を検出し、自動対応につなげられます。

</details>

### 問6

ある小売企業では、注文サービスが注文を確定するたびに、分析、会員ポイント、レコメンド、不正検知、通知の 5 つのチーム（それぞれ別の AWS アカウント）が処理を行います。今後も受け取り側のチームは増える予定で、注文サービスのチームは、受け取り側が増えるたびに自分たちのコードを変更したくありません。各チームは自分に必要な注文イベントだけを受け取り、障害から復旧した後に過去のイベントを再処理できる必要があります。最も適切な設計はどれですか。

- A. 注文サービスから、各チームの API を順に同期で呼び出す。
- B. 注文サービスは中央のカスタムイベントバスに OrderPlaced イベントを発行する。受け取り側ごとに、必要なイベントだけに絞り込むイベントパターンのルールを作成し、各チームのアカウントのイベントバスをターゲットにする。ターゲットごとに DLQ を設定し、中央のバスのアーカイブを有効にして再生できるようにする。
- C. Step Functions のワークフローで 5 つのチームの処理を順に呼び出し、新しいチームが増えたらワークフローに手順を追加する。
- D. 1 つの SQS 標準キューに注文イベントを送り、各チームのアプリケーションがそのキューをポーリングする。

<details>
<summary>解答と解説</summary>

**正解: B**

**解説**: 発行側を変えずに受け取り側を追加できるコレオグラフィの典型です。EventBridge のルールは受け取り側ごとに独立して追加でき、イベントパターンで必要なイベントだけに絞り込めます。他のアカウントのイベントバスをターゲットにでき、アーカイブと再生で過去のイベントを再処理できます。

**各選択肢の検討**
- A: ✗ 受け取り側が増えるたびに注文サービスの変更が必要で、1 つのチームの障害や遅延が注文の処理に波及します。
- B: ✓ 疎結合、選択的な受信、アカウント間の配信、再処理のすべてを満たします。
- C: ✗ 受け取り側が増えるたびにワークフローの変更が必要で、独立した処理を不必要に結合します。
- D: ✗ 1 つのキューを共有すると、各メッセージはどれか 1 つのチームだけが処理します（競合コンシューマー）。全チームに届きません。

</details>
